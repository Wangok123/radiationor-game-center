# 滑动窗口、二分与单调队列

> 本文为学习笔记整理。示例用于说明概念，性能、版本兼容与平台行为需结合实际环境验证。

## 核心方法

这些题型的共同点不是记模板，而是维护一个随输入单调推进的不变量：窗口左/右边界、答案可行性或候选元素的支配关系。

在动手前先回答四件事：状态是否只随指针前进而可增量更新？`check(x)` 是否真单调？某个候选何时能被另一个候选永久支配？边界（空、重复、负数、溢出）是否改变不变量？四个问题中任意一个不成立，套模板通常只会得到“样例正确”的代码。

## 滑动窗口

适用于连续区间，且当右边界推进后可以通过移动左边界恢复约束。先定义窗口代表的状态和“何时非法”，再决定收缩时机。若约束不具备单调性，普通双指针可能失效。

```text
for right in range(n):
    add(a[right])
    while window_is_invalid():
        remove(a[left]); left += 1
    update_answer(left, right)
```

### 不变量与适用边界

上面的伪代码适用于“最长合法窗口”。最短满足窗口则应在条件满足时先记录答案，再尝试缩小窗口；两者不能直接共用收缩条件。

一个标准“最短满足窗口”通常维护：处理完 `right` 后，`[left, right]` 合法，且继续右移 `left` 会使它非法。此时每个 `left` 和 `right` 各至多前进 `n` 次，才有 O(n) 的复杂度。

但不是所有区间和/计数问题都满足单调收缩。例如元素允许负数时，“窗口和至少为 K”不保证右移 `right` 后只需右移 `left` 就能恢复有序关系；这类问题可能需要前缀和加单调队列、平衡树或其他模型。窗口可维护的统计量也必须支持增量 `add/remove`，如频次、不同元素数、至多 K 类；若每次移除都要重算全窗口，复杂度已经不是 O(n)。

### 证明检查表

1. 写清窗口状态代表什么，例如 `count[x]` 是否正好等于当前闭区间频次。
2. 证明右指针只前进不会漏掉候选解。
3. 证明收缩循环结束时，窗口满足要记录的极小/极大性质。
4. 证明每个元素的进入、删除和任何辅助结构操作是有界的。
5. 分开处理 `k = 0`、空数组、目标不存在和索引溢出；不要让主循环隐含这些语义。

## 二分答案

不是“有序数组才二分”，而是答案空间上的 predicate 必须单调：`false false ... true true` 或反之。先写清 `check(x)` 的含义和边界，再决定寻找第一个 true、最后一个 true 或精确值。最常见错误是边界闭开区间混用。

### 循环契约

将边界设计写成一句自然语言，而不是记 `mid` 模板。一个稳健的“第一个 true”版本可使用半开区间：`[lo, hi)` 中仍可能存在答案，区间左侧已知 false，右侧已知 true 或是哨兵。循环每次严格缩小 `hi - lo`，退出时 `lo == hi`。

```text
lo = lower_bound
hi = upper_bound_exclusive
while lo < hi:
    mid = lo + (hi - lo) / 2   # 避免 lo + hi 溢出
    if check(mid):
        hi = mid
    else:
        lo = mid + 1
return lo                      # 必须再判断是否位于有效答案域
```

对于实数答案，循环次数和误差界替代离散终止条件；对于“最大可行值”，可把 predicate 反向，或先求第一个不可行值再减一。两种写法不能混用闭区间和半开区间的后置处理。

### `check` 的工程边界

`check(x)` 必须是纯粹、可重复且单调的判断。随机数、读取不断变化的缓存、网络响应、浮点临界值或修改全局状态，都会让二分失去数学前提。若 `check` 会触发磁盘、网络、GC 或昂贵 Unity API，O(log N) 次调用仍可能不适合作为热路径；先纯化 `check` 或缓存其输入。

## 单调队列

维护可能成为窗口最值的候选下标：新元素进入时弹出被支配的尾部，窗口移动时弹出过期头部。每个下标最多进出一次，整体 O(n)。队列存下标而不是值，才能判断过期和处理重复值。

### 支配关系与摊还分析

对滑窗最大值，若 `i < j` 且 `a[i] <= a[j]`，那么在 `j` 仍处于未来窗口时，`i` 不可能再次成为最大值：`j` 更晚过期且值不小。因此 `i` 可在 `j` 入队时从队尾删除。反过来，队首只因过期被删除。每个下标最多入队一次、被队尾支配删除一次或从队首过期删除一次，故总操作 O(n)，并非每步都 O(1) 的最坏情况。

相等元素的处理必须和需求一致：用 `<=` 删除旧元素，队列偏向保留最新下标；用 `<` 保留多个相等候选。两者都能求最大值，但会改变“返回最早还是最晚位置”、内存峰值和调试 trace，不能随手替换。

```text
for i in 0..n-1:
    while deque not empty and a[deque.back] <= a[i]:
        deque.pop_back()       # 新元素永久支配旧元素
    deque.push_back(i)
    while deque.front <= i-k:
        deque.pop_front()      # 队首已不在窗口
    if i >= k-1:
        answer.add(a[deque.front])
```

### 何时不要用单调队列

- 需要任意删除而非只从窗口左侧过期时，普通 deque 不再足够。
- 需要中位数、任意分位数或同时维护复杂集合属性时，可能需要双堆、平衡树或 Fenwick/segment tree。
- 数据流没有明确过期边界时，应先定义 retention policy；无限队列不是“滑动窗口”。

## 工程映射与反例

| 模型 | 游戏/服务端映射 | 首先要验证的反例 |
| --- | --- | --- |
| 滑动窗口 | 最近 N tick 输入、限时事件计数、玩家行为速率 | tick 是否单调，掉线重连是否插入旧事件。 |
| 二分答案 | 资源预算下的最大单位数、难度参数、批处理上限 | `check` 是否因随机性、缓存或副作用而失去单调性。 |
| 单调队列 | 最近窗口内伤害峰值、延迟峰值、限流峰值 | 过期条件是逻辑 tick 还是墙钟；乱序事件如何处理。 |

算法复杂度并不等于系统成本。容器分配、比较器、数据局部性、日志和 Unity API 边界都可能主导真实耗时。

## 工程验证

为每个实现写一个 O(n^2) 或暴力解作为小数据 oracle，随机生成负数、重复值、空输入、窗口大于数组和边界答案，比较结果与复杂度。不要只用“看起来覆盖”的几个样例。

### 属性测试建议

- 滑窗：暴力枚举全部子数组，与优化算法的长度/数量/边界完全一致；生成负数、极值、全相同、`k=0` 和 `k>n`。
- 二分：在小答案域穷举 `check`，断言单调性本身，再断言返回值是目标边界。若 predicate 已不单调，测试应先失败而不是调算法。
- 单调队列：对每一个输出窗口，用暴力 `max/min` 验证值和下标；随机重复值可以暴露 `<=`/`<` 和过期顺序错误。
- 记录随机 seed、输入序列和失败 shrink 结果。发现反例后，将其固定成 regression case，而不是只改一次代码。
