# B+Tree 索引与查询计划

> 本文为学习笔记整理。示例用于说明概念，性能、版本兼容与平台行为需结合实际环境验证。

## 核心结论

B+ 树索引用有序页结构降低定位范围，并让范围扫描按键顺序进行。索引是否有效取决于查询谓词、组合列顺序、选择性、覆盖列、排序和真实数据分布；不能仅凭“建了索引”判断。使用 `EXPLAIN ANALYZE`、实际行数和延迟验证，索引也会增加写放大、空间和维护成本。

## 为什么组合索引有顺序

索引 `(a, b, c)` 按 `a` 再 `b` 再 `c` 排序。等值谓词通常能连续缩小前缀；对前导列进行范围筛选后，后续列通常不能再像等值前缀那样用于进一步定位，但可能仍服务覆盖或排序。所谓“最左前缀”是这个排序事实的结果，不是口诀。

InnoDB 的聚簇索引叶子保存行数据；二级索引叶子包含二级键和对应主键值，查到二级键后，若投影列不在二级索引中，通常还需按主键再访问聚簇记录（回表）。因此主键长度会影响二级索引体积；覆盖索引能减少回表，但增加索引空间与写维护。具体执行计划仍要由实际 MySQL 版本、schema 和统计信息确认。

## 从查询形状推导索引

把查询抽象为过滤、排序、投影、分页，再按业务优先级推导候选索引。常用顺序是：等值列前置，随后考虑范围/排序列；但不是机械规则，要检查选择性、排序方向和是否已有可用前缀。

```sql
SELECT item_id, quantity, updated_at
FROM inventory
WHERE user_id = ? AND state = ?
ORDER BY updated_at DESC, item_id DESC
LIMIT 50;
```

候选索引可以从 `(user_id, state, updated_at, item_id)` 开始评估。需要回答：`user_id/state` 是否等值、是否存在 state 低选择性、排序是否由索引满足、是否可覆盖返回列、`updated_at` 是否有大量相同值、游标分页是否有稳定唯一 tie-break。最终不是“索引列齐了”，而是 `EXPLAIN ANALYZE` 显示访问路径对目标分布有效，同时写成本可接受。

### 前缀和范围边界

对 `(a,b,c)`：

| 谓词 | 常见利用方式 | 需要观察 |
| --- | --- | --- |
| `a=? AND b=? AND c=?` | 完整复合键定位 | rows、唯一性、覆盖。 |
| `a=? AND b>=? AND c=?` | 前缀加 `b` 范围扫描；`c` 可能作为过滤而非进一步缩窄连续范围 | 扫描行与返回行差距、ICP。 |
| `b=?` | 缺少最左列，通常不能直接按同一方式定位 | 是否存在 skip scan/其它索引，不能假定。 |
| `a=? ORDER BY b,c` | 可按后续键顺序输出 | 方向、collation、隐含主键顺序及实际计划。 |

索引能被 optimizer 考虑，不等于计划一定选择它；统计信息、代价估算、参数分布和数据倾斜都会改变选择。参数嗅探/计划缓存也可能使一个平均数据分布的计划不适合极端 tenant。

## 查询诊断流程

1. 写出目标：读多少数据、按什么顺序、返回哪些列、延迟预算是什么。
2. 用真实或代表性分布执行 `EXPLAIN ANALYZE`，比较 estimated rows 与 actual rows。
3. 识别全表扫描、过多回表、filesort、临时表、低选择性或隐式类型转换。
4. 提出一个最小索引变化，并评估写入 QPS、索引大小和现有查询的副作用。
5. 上线后监控 p95/p99、扫描行数、buffer pool 命中、写放大和慢日志。

`EXPLAIN` 是估计计划，`EXPLAIN ANALYZE` 会实际执行并输出运行统计；它可能改变缓存状态、消耗资源或触发真实查询副作用，因此生产诊断应谨慎挑选安全查询和代表性参数。比较 estimate 与 actual：行数估计偏差常是统计/相关性问题；实际扫描远多于返回行则可能是索引范围不合适、过滤发生太晚或数据分布倾斜。

## 查询计划读数合同

分析时不要把某一个 `type/key/Extra` 字段机械翻译成“快/慢”。按执行树读取：

1. 从叶子访问路径确认读了哪些索引/表、索引范围是什么。
2. 看每个节点估计 rows 与实际 rows、循环次数和耗时。
3. 确认过滤、join、排序、聚合在哪个节点完成，数据是否过早放大。
4. 对比结果正确性、稳定排序、事务隔离和分页要求。
5. 在冷/热缓存和代表性参数上重复，避免只解释一次幸运缓存命中。

`Using filesort` 表示需要额外排序过程，不等同于“必然落盘”；临时表、回表也要看行数和实际耗时。反过来，一个看似 `range` 的计划若扫了几十万行再过滤，同样可能很慢。

## 分页与排序的正确性

`LIMIT offset, size` 通常需要跳过前面的结果，offset 增大时扫描工作也可能增长。keyset pagination 使用上一页末尾稳定排序键作为边界：

```sql
SELECT ...
FROM events
WHERE user_id = ?
  AND (created_at, event_id) < (?, ?)
ORDER BY created_at DESC, event_id DESC
LIMIT 100;
```

游标必须形成全序，`created_at` 相同需唯一 tie-break。若排序键可变或分页期间数据持续插入，还要定义一致性视图：允许新数据进入后续页、固定 snapshot，还是接受轻微变化。索引设计不能脱离分页 API 语义。

## 索引的写成本与数据分布

每个二级索引都会消耗磁盘/缓存，并在 insert、delete、相关列 update 时维护；宽索引会减少每页条目数，增加树高或页分裂概率。更新索引列可能形成 delete+insert 工作。低选择性列并非永远不该索引：若与高选择性列组合、用于覆盖/排序，仍可能有价值；是否有价值由查询实测决定。

一个合理的变更至少对比：目标查询 p95/p99 和扫描行、所有相关写路径的延迟/QPS、索引大小、buffer pool 使用、复制/备份体积。删除“看起来重复”的索引前还需检查约束用途、前缀覆盖、不同排序方向以及部署回滚窗口。

## 常见设计

| 场景 | 查询形状 | 索引推导 |
| --- | --- | --- |
| 玩家背包 | `user_id = ?`，按更新时间分页 | 以 `user_id` 开头，结合排序/游标列。 |
| 领奖幂等 | 等值查唯一业务键 | 唯一复合索引表达业务不变量。 |
| 排行榜 | 分数排序、范围读取 | 先确认读写模型；高写入场景常转 Redis/专用排序结构，不把关系库当万能排行榜。 |

## 反模式

- 只因某列出现在 `WHERE` 就单列建索引，忽视组合查询与写成本。
- `SELECT *` 使覆盖索引失效并扩大回表/网络传输。
- offset 很大的分页；改用稳定排序键的 keyset pagination。
- 用函数包装索引列或让参数类型不匹配，却期待索引保持高选择性。
- 只看估计 EXPLAIN 就宣布生产收益，未比较实际行数和代表性参数。
- 为一个读查询创建宽覆盖索引，却不测写放大、缓存命中和存储体积。
- 排序没有唯一 tie-break，分页时出现重复/漏项后归咎于数据库随机性。
